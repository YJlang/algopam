# [알고팜 3주차] 프로그래머스 마법의 엘리베이터 - 예제는 맞는데 제출하면 틀리는 '5'의 함정

예제 입력(16, 2554)은 둘 다 정확히 맞았는데, 제출하면 일부 케이스에서 틀리는 문제였다. 원인은 딱 하나, **끝자리가 정확히 5일 때**의 처리였다. 이 글은 그 한 줄짜리 실수를 추적하고, 그리디와 DP 두 가지 풀이로 다시 정리한 오답 노트다.

문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/148653

## 문제 정보

- 분류 감각: 그리디(Greedy), 자릿수 분해 — 프로그래머스 Lv.2
- 제한사항: `1 ≤ storey ≤ 100,000,000` (최대 1억, 즉 최대 9자리)

## 문제 설명

마법의 엘리베이터에는 `-1, +1, -10, +10, -100, +100 …` 처럼 **절댓값이 10의 거듭제곱(10^c, c ≥ 0)** 인 버튼들이 있다. 버튼을 누르면 현재 층수에 그 값을 더한 층으로 이동하고, **버튼 한 번을 누를 때마다 마법의 돌을 1개** 쓴다. (단, 더한 결과가 0보다 작으면 움직이지 않는다.)

`storey`층에서 **0층까지 내려가는 데 필요한 마법의 돌의 최소 개수**를 구하면 된다.

핵심 포인트는 **버튼 비용이 크기와 무관**하다는 것이다. `-1`을 누르든 `-100`을 누르든 똑같이 돌 1개다. 그래서 "거리"가 아니라 "버튼을 누른 횟수"를 최소화하는 문제다.

## 입력 형식

- `storey`: 민수가 있는 층을 나타내는 정수 (`1 ≤ storey ≤ 100,000,000`)

## 출력 형식

- 0층까지 가는 데 필요한 마법의 돌(버튼 누름)의 최소 개수를 정수로 `return`

## 예제 입력 1

```text
storey = 16
```

## 예제 출력 1

```text
6
```

> `+1`을 4번(16→20), `-10`을 2번(20→0) → 총 6번. (`-1`을 6번 + `-10`을 1번 = 7번보다 적다.)

## 예제 입력 2

```text
storey = 2554
```

## 예제 출력 2

```text
16
```

## 접근 아이디어

버튼은 `±1, ±10, ±100 …` 즉 **각 자릿수만 건드린다**. `+1`을 계속 누르다 일의 자리가 10이 되면 → 십의 자리로 **받아올림(+1)** 이 넘어간다. 그리고 받아올림은 항상 **아래 자리 → 위 자리** 한 방향으로만 흐른다.

그래서 **일의 자리부터** 한 자리씩 처리하면 된다. 어떤 자리의 숫자 `d`를 0으로 만드는 방법은 딱 두 가지다.

| 선택 | 동작 | 비용 |
| --- | --- | --- |
| 내림(↓) | `-1`을 `d`번 → 그 자리 0으로 | `d` |
| 올림(↑) | `+1`을 `10 - d`번 → 10을 채워 윗자리로 +1 받아올림 | `10 - d` |

- `d < 5` → `d < 10 - d` 이므로 **내림이 이득**
- `d > 5` → `10 - d < d` 이므로 **올림이 이득** (윗자리에 +1 떠넘기는 비용은 많아야 1이고, 올림으로 아끼는 양은 최소 2라 항상 안전하다)
- `d == 5` → 이번 자리만 보면 내림(5)·올림(5) **비용이 같다**. 그래서 **윗자리를 봐야 한다.** ← 여기가 함정

## 원래 작성했던 코드

처음엔 "5보다 크면 올리고, 아니면 내린다"로 단순하게 분기했다. 예제 16, 2554가 둘 다 맞길래 통과인 줄 알았다.

```python
def solution(storey):
    answer = 0
    while storey > 0:
        digit = storey % 10
        if digit > 5:            # 5 '초과'일 때만 올림
            answer += 10 - digit
            storey += 10         # +10 후 //10 → 윗자리로 +1 받아올림 (이 부분은 정상)
        else:                    # 0~5는 전부 내림 처리  ← digit == 5도 여기로 빠진다 (버그)
            answer += digit
        storey //= 10
    return answer
```

## 이 코드에서 하려던 것

의도 자체는 위 접근 아이디어와 같았다. 그리고 사실 **두 부분은 맞게 짰다.**

- `digit > 5`일 때 `answer += 10 - digit`로 올림 비용을 더한 것 — 맞다.
- `storey += 10` 후 루프 끝에서 `storey //= 10` 하는 것 — `(storey + 10) // 10 == storey // 10 + 1`이라 **받아올림(+1)이 정확히 반영**된다. 맞다.

진짜 문제는 단 하나, **`digit == 5`가 `else`로 빠져서 "무조건 내림"으로 처리**된다는 점이다. `if digit > 5`는 5를 포함하지 않으므로 5는 항상 내려버린다.

## 약했던 점과 반례

`d == 5`일 때 윗자리가 5 이상이면 **올리는 게 이득**인데, 원래 코드는 이 경우를 절대 잡지 못한다. 예제(16, 2554)에는 마침 이 상황이 없어서 통과했을 뿐이다.

```text
입력
storey = 65
```

```text
잘못된 출력: 10
정답:        9
```

원래 코드의 실행을 따라가 보면:

```text
65 | digit 5 → else(내림) +5 (=5)  → storey 6
 6 | digit 6 → 올림 +4 (=9), +10→16 → //10 → 1
 1 | digit 1 → else(내림) +1 (=10) → 0
→ 10
```

하지만 65는 `+1`을 5번 눌러 70으로 올리고(받아올림), 70 → 100 → 0으로 가면 `5 + 3 + 1 = 9`번이면 된다. 일의 자리 5에서 **올렸어야** 했다.

같은 이유로 `555`도 깨진다.

```text
입력
storey = 555
```

```text
잘못된 출력: 15   (5+5+5, 전부 내림)
정답:        14   (555→56→6→1: 5+4+4+1)
```

## 개선 풀이 1: 그리디 + d==5일 때 윗자리 확인

`d == 5`인 경우만 분리해서, **바로 윗자리 숫자가 5 이상이면 올림**, 아니면 내림으로 처리한다. (윗자리도 5 이상이면 어차피 올라갈 자리라, 미리 +1 받아두는 쪽이 더 싸기 때문이다.)

```python
def solution(storey):
    answer = 0
    while storey > 0:
        d = storey % 10                      # 맨 끝자리

        if d < 5:                            # 작으면 → 내림
            answer += d
            storey //= 10                    # 올림 없이 윗자리로
        elif d > 5:                          # 크면 → 올림
            answer += 10 - d
            storey = storey // 10 + 1        # 윗자리로 +1 받아올림
        else:                                # d == 5
            if (storey // 10) % 10 >= 5:     # 윗자리도 크면 올리는 게 이득
                answer += 5
                storey = storey // 10 + 1
            else:                            # 아니면 그냥 내림
                answer += 5
                storey //= 10
    return answer
```

핵심은 `storey // 10`(올림 없음) vs `storey // 10 + 1`(올림 있음)의 차이다. 코드가 짧고 직관적이지만, `d == 5`의 타이브레이크를 직접 다뤄야 해서 처음 실수한 바로 그 지점이다.

## 개선 풀이 2: DP — "올림을 내보낼지" 두 상태로 들고 가기

`5`의 타이브레이크가 찜찜하다면, **각 자리에서 내림/올림 둘 다 고려**하고 최솟값만 들고 가는 DP가 더 안전하다. 자릿수를 낮은 자리부터 보면서 두 상태를 유지한다.

- `keep`: 지금까지 처리한 아랫자리들이 **윗자리로 올림을 내보내지 않은** 경우의 최소 비용
- `up`: 아랫자리들이 **윗자리로 +1 올림을 내보낸** 경우의 최소 비용

```python
def solution(storey):
    keep, up = 0, float('inf')               # keep: 올림 없음, up: 윗자리로 +1 올림
    for ch in reversed(str(storey)):         # 낮은 자리 → 높은 자리
        d = int(ch)
        # 올림이 들어오면 이 자리의 실제 값은 d+1이 된다
        new_keep = min(keep + d,       up + (d + 1))       # 이 자리에서 올림을 안 내보냄
        new_up   = min(keep + (10 - d), up + (10 - (d + 1)))  # 이 자리에서 윗자리로 올림
        keep, up = new_keep, new_up
    return min(keep, up + 1)                 # 최상위에서 올림이 남으면 -10^k 한 번 더(+1)
```

마지막에 `up + 1`을 비교하는 이유: 최상위 자리에서까지 올림이 남으면(예: 95 → 100) 한 자리 위로 올라간 셈이라 `-10^k`를 한 번 더 눌러야 하기 때문이다. (예: `95 → +1×5 → 100 → -100 → 0`, 6번.)

`d == 5` 같은 특수 분기가 전혀 없다. 매 자리에서 "내림/올림"을 모두 펼쳐 min을 취하므로, **올림이 윗자리에 미치는 영향까지 자동으로 반영**된다. 그리디의 타이브레이크 규칙을 외우지 않아도 된다는 게 장점이고, 대신 상태 두 개를 들고 가는 점화식을 세워야 한다.

## 시간 복잡도와 공간 복잡도

여기서 `n`은 **`storey`의 자릿수**(= ⌊log₁₀(storey)⌋ + 1)다. `storey ≤ 1억`이므로 `n ≤ 9`.

| 풀이 | 시간 복잡도 | 공간 복잡도 | 한 줄 메모 |
| --- | --- | --- | --- |
| 처음 (틀린) 풀이 | `O(log₁₀ N)` | `O(1)` | 복잡도는 정상, 정답성이 틀림 (d==5 미처리) |
| 개선 1: 그리디 | `O(log₁₀ N)` | `O(1)` | 코드 짧음, 5 타이브레이크 직접 처리 |
| 개선 2: DP | `O(log₁₀ N)` | `O(log₁₀ N)` | str 변환 때문에 자릿수만큼 공간, 특수분기 없음 |

유도를 자세히 보면:

- **그리디**: `while` 루프가 매 회전마다 `storey`를 `//10`(또는 `//10 + 1`)로 줄인다. 즉 한 회전에 자리 하나씩 사라지므로 **반복 횟수 = 자릿수 = `O(log₁₀ N)`**. 각 회전 안은 나머지·나눗셈·비교뿐이라 `O(1)`. 추가 메모리는 `answer` 하나라 `O(1)`. 병목은 이 단일 `while` 루프다.
- **DP**: `str(storey)`로 자릿수만큼 문자를 만들고(`O(n)` 시간·공간), 그 길이만큼 루프를 돈다. 매 단계는 `min` 두 번이라 `O(1)`. 합쳐서 **시간 `O(n) = O(log₁₀ N)`**, 공간은 문자열 때문에 `O(n)`. (`str` 대신 `% 10`/`// 10` 정수 연산으로 짜면 공간을 `O(1)`로 줄일 수 있다.)
- **세 풀이 모두 시간은 `O(log₁₀ N)`** 으로 같다. 처음 풀이가 틀린 건 느려서가 아니라 **답이 틀려서**였다는 점이 이 문제의 교훈이다.

제한과 연결해 보면, 만약 "`-1`을 한 번씩 눌러 0까지 시뮬레이션"하는 `O(N)` 풀이를 짰다면 최악의 입력에서 약 `1e8`번을 돌아 **시간 초과** 위험이 있다. 반면 자릿수 기반 풀이는 `N`이 1억이어도 **단 9번**의 반복이면 끝난다("입력 자릿수가 1개 늘어야 반복이 1번 는다" = 로그 증가). 그래서 자릿수 분해가 핵심이다.

## 이번 문제에서 배운 점

- **경계값(`>` vs `>=`)을 흘려보내지 말자.** `if digit > 5`는 5를 빼먹는다. 비용이 같은 타이(`d == 5`)에서는 "그다음에 미치는 영향"으로 결정해야 한다.
- **예제 통과 ≠ 정답.** 주어진 예제(16, 2554)에는 우연히 함정 케이스가 없었다. 손으로 작은 반례(`65`, `555`)를 만들어 보는 습관이 제출 전 검증에 강력하다.
- **그리디의 타이브레이크가 불안하면 DP로 안전하게.** 같은 `O(log N)`이라도, 매 자리에서 두 선택을 모두 펼쳐 min을 취하면 특수 분기 없이 받아올림 효과까지 자동 반영된다.
- **버튼 비용이 크기와 무관**하다는 문제의 성질이 "자릿수 분해 + 로그 시간" 풀이의 출발점이었다. 시뮬레이션(`O(N)`) 대신 자릿수(`O(log N)`)로 보는 시각 전환이 제한(1억)을 통과시킨다.
