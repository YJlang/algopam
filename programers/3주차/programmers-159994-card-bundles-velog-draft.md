# [알고팜 3주차] 프로그래머스 카드 뭉치 - 카드는 앞에서부터 꺼내야 한다

예제는 둘 다 통과했는데 제출하면 일부 케이스가 틀리는 문제였다. 처음에는 `goal`을 거꾸로 돌면서 카드 뭉치의 **뒤에서부터** 맞춰봤는데, 알고 보니 이 문제의 핵심은 **카드를 뭉치의 앞(맨 위)에서부터만 꺼낼 수 있다**는 점이었다. 방향을 반대로 잡으니 예제는 우연히 맞고 숨은 테스트에서 터졌다.

문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/159994

## 문제 정보

- 출처: 프로그래머스 코딩테스트 연습 (Lv.1)
- 플랫폼 분류: **스택/큐** — "한쪽 끝에서 정해진 순서대로만 꺼내는" 큐(FIFO) 모델을 묻는 단원이다.
- 사용한 기법: **투 포인터 + 그리디** (각 뭉치를 `deque`로 만들지 않고 인덱스로 큐 동작을 흉내 낸다)
- 문제 번호: 159994

## 문제 설명

두 개의 카드 뭉치 `cards1`, `cards2`가 있다. 각 뭉치의 카드는 **맨 앞에서부터 순서대로 한 장씩만** 사용할 수 있다.

규칙은 이렇다.

- 한 번 사용한 카드는 다시 사용할 수 없다.
- 카드를 건너뛰고 더 뒤의 카드를 먼저 쓸 수 없다. (각 뭉치 안에서 순서 고정)
- 두 뭉치 중 어느 쪽 카드를 쓸지는 자유롭게 고를 수 있다.

이 규칙을 지키면서 카드를 뽑아 목표 문자열 배열 `goal`을 순서대로 만들 수 있으면 `"Yes"`, 만들 수 없으면 `"No"`를 반환한다.

## 입력 / 제한사항

- `1 ≤ cards1의 길이, cards2의 길이 ≤ 10`
- `1 ≤ 각 단어의 길이 ≤ 10`
- `cards1`과 `cards2`에는 서로 다른 단어만 들어 있다. (중복 단어 없음)
- `2 ≤ goal의 길이 ≤ cards1의 길이 + cards2의 길이`
- `goal`의 원소는 `cards1`, `cards2`의 원소들로만 이루어져 있다.
- 모든 문자열은 소문자로만 구성된다.

> 여기서 가장 중요한 제한은 `goal`의 길이가 **두 뭉치 전체 길이보다 짧을 수 있다**는 점이다. 즉, 카드를 전부 쓰지 않고 앞쪽 일부만 써서 `goal`을 만들 수도 있다. 이 한 줄을 놓치면 나처럼 뒤에서부터 맞추는 풀이를 짜게 된다.

## 출력 형식

- `goal`을 규칙대로 만들 수 있으면 `"Yes"`, 아니면 `"No"`를 반환한다.

## 예제 입력 / 출력

| cards1 | cards2 | goal | result |
| --- | --- | --- | --- |
| `["i", "drink", "water"]` | `["want", "to"]` | `["i", "want", "to", "drink", "water"]` | `"Yes"` |
| `["i", "water", "drink"]` | `["want", "to"]` | `["i", "want", "to", "drink", "water"]` | `"No"` |

- 예제 1: `cards1`에서 `i` → `cards2`에서 `want`, `to` → 다시 `cards1`에서 `drink`, `water` 순서로 꺼내면 `goal`이 완성된다. → `"Yes"`
- 예제 2: `drink`보다 `water`가 `cards1`에서 먼저 나오기 때문에, `goal`이 요구하는 `drink` → `water` 순서를 만들 수 없다. → `"No"`

두 예제 모두 `goal`의 길이가 `3 + 2 = 5`로 **카드를 전부 소진**한다는 점을 기억해두자. 뒤에서 설명할 내 오답이 예제만 통과한 이유가 바로 여기에 있다.

## 접근 아이디어

각 뭉치는 앞에서부터만 꺼낼 수 있으므로, 두 뭉치에 각각 "지금 꺼낼 수 있는 맨 앞 카드"를 가리키는 포인터를 두면 된다.

`goal`을 앞에서부터 한 단어씩 보면서,

1. `cards1`의 현재 맨 앞 카드와 같으면 그 카드를 쓰고 `cards1` 포인터를 한 칸 앞으로,
2. 아니면 `cards2`의 현재 맨 앞 카드와 같은지 보고 맞으면 `cards2` 포인터를 한 칸,
3. 둘 다 아니면 그 단어는 만들 수 없으므로 즉시 `"No"`.

문제 제한에서 **두 뭉치의 단어가 서로 겹치지 않는다**고 했기 때문에, 어떤 단어가 두 뭉치의 맨 앞과 동시에 일치하는 애매한 상황이 생기지 않는다. 그래서 "맞으면 바로 그 뭉치를 쓴다"는 단순 그리디가 항상 옳다.

## 원래 작성했던 코드 (오답)

처음엔 "어차피 양쪽 끝을 맞춰가면 되겠지" 하고 `goal`을 **뒤에서부터** 돌면서 각 뭉치의 **마지막 카드**와 비교했다.

```python
def solution(cards1, cards2, goal):
    answer = ''
    c1 = len(cards1)   # cards1에서 아직 안 쓴 카드 개수 (뒤에서부터 본다)
    c2 = len(cards2)   # cards2에서 아직 안 쓴 카드 개수

    for i in reversed(goal):          # goal을 뒤에서부터 본다
        if c1 > 0 and cards1[c1-1] == i:   # cards1의 '마지막' 카드와 비교
            c1 -= 1
        elif c2 > 0 and cards2[c2-1] == i: # cards2의 '마지막' 카드와 비교
            c2 -= 1
        else:
            answer = 'No'
            break

    if answer == '':
        answer = 'Yes'
    return answer
```

## 이 코드에서 하려던 것

아이디어 자체는 투 포인터가 맞다. `goal`을 한 번 훑으면서 두 뭉치를 한 칸씩 줄여나가는 구조다.

문제는 **방향**이었다. 카드는 뭉치의 **앞(맨 위)** 에서만 꺼낼 수 있는데, 이 코드는 `reversed(goal)`로 뒤에서부터 보면서 `cards1[c1-1]`, 즉 뭉치의 **마지막 카드**와 비교한다. 이건 "카드를 맨 뒤(맨 아래)에서부터 꺼낼 수 있다"고 가정한 셈이라, 실제 규칙과 정반대다.

## 약했던 점과 반례

왜 예제는 통과했을까? 예제 1, 2는 모두 `goal`이 두 뭉치를 **전부** 사용한다(`길이 5 = 3 + 2`). 카드를 전부 쓰면 "앞에서부터 본 것"과 "뒤에서부터 본 것"이 결국 같은 카드 집합을 훑게 되어, 뒤에서 맞추는 풀이도 우연히 정답과 같은 결과를 낸다.

하지만 `goal`이 **앞쪽 일부 카드만** 쓰는 경우엔 바로 깨진다.

```text
cards1 = ["a", "b"]
cards2 = ["c", "d"]
goal   = ["a", "c"]
```

```text
정답:        Yes   (cards1 앞에서 "a", cards2 앞에서 "c"를 꺼내면 됨)
오답 코드:   No
```

오답 코드를 그대로 따라가 보면,

- `reversed(goal)` = `["c", "a"]`
- 첫 단어 `"c"`: `cards1`의 마지막 카드 `"b"` ≠ `"c"`, `cards2`의 마지막 카드 `"d"` ≠ `"c"` → 곧바로 `"No"`

`goal`이 필요로 하는 `a`, `c`는 두 뭉치의 **앞쪽**에 있는데, 코드는 **뒤쪽**부터 보니 첫 비교에서 바로 실패한다. 결국 이 문제는 "투 포인터를 쓰느냐"가 아니라 **"어느 쪽 끝에서 꺼내느냐"** 가 핵심이었다.

## 개선 풀이: 앞에서부터 보는 투 포인터 (정답)

방향만 바로잡으면 된다. `goal`을 앞에서부터 보고, 각 뭉치의 **맨 앞 카드**(`cards1[i]`, `cards2[j]`)와 비교한다.

```python
def solution(cards1, cards2, goal):
    i = 0   # cards1에서 다음에 꺼낼 '맨 앞' 카드의 위치
    j = 0   # cards2에서 다음에 꺼낼 '맨 앞' 카드의 위치

    for word in goal:                       # goal을 앞에서부터 한 단어씩
        if i < len(cards1) and cards1[i] == word:
            i += 1                          # cards1의 맨 앞 카드를 사용
        elif j < len(cards2) and cards2[j] == word:
            j += 1                          # cards2의 맨 앞 카드를 사용
        else:
            return "No"                     # 두 뭉치 맨 앞 어느 쪽도 못 맞추면 불가능
    return "Yes"
```

핵심은 포인터가 항상 **0에서 시작해 앞으로만 증가**한다는 점이다. `cards1[i]`는 언제나 "아직 안 쓴 카드 중 가장 위에 있는 카드"를 가리킨다. 카드를 꺼낸다는 행위가 포인터를 `+1` 하는 것과 정확히 같다.

`i < len(cards1)` 같은 범위 체크를 먼저 두는 이유는, 한 뭉치를 다 써버린 뒤에 인덱스를 벗어나 접근하는 것을 막기 위해서다. (이 검사를 빼면 `IndexError`가 난다.)

## 다른 풀이: 큐(deque)로 그대로 옮기기 (정석)

이 문제가 "스택/큐" 단원에 있는 이유를 코드로 드러내는 풀이다. 각 카드 뭉치를 `deque`로 만들고 맨 앞에서 한 장씩 꺼내면(`popleft`) 문제 상황이 그대로 코드가 된다.

```python
from collections import deque

def solution(cards1, cards2, goal):
    c1 = deque(cards1)   # 큐: 왼쪽(맨 앞)에서만 꺼낸다
    c2 = deque(cards2)

    for word in goal:
        if c1 and c1[0] == word:    # cards1 맨 앞 카드 확인
            c1.popleft()            # 한 장 꺼내 사용
        elif c2 and c2[0] == word:  # cards2 맨 앞 카드 확인
            c2.popleft()
        else:
            return "No"
    return "Yes"
```

투 포인터 풀이와 **하는 일은 완전히 같다**. `c1[0]`이 `cards1[i]`에, `c1.popleft()`가 `i += 1`에 대응한다. 즉 투 포인터는 `deque`를 실제로 만들지 않고 인덱스만 옮겨 같은 큐 동작을 더 가볍게 흉내 낸 것이다.

- **deque 버전**: 문제의 큐 개념이 코드에 그대로 드러나 읽기 쉽다. 대신 뭉치를 큐로 복사하는 만큼 추가 메모리를 쓴다.
- **투 포인터 버전**: 추가 자료구조 없이 인덱스 두 개만 쓴다. 더 가볍지만 "큐를 쓰고 있다"는 의도가 코드에 덜 드러난다.

두 풀이의 시간 복잡도는 같으므로, 입력이 아주 작은 이 문제에서는 취향대로 골라도 된다. 자료구조의 의미를 드러내려면 deque, 군더더기 없는 효율을 원하면 투 포인터다.

## 시간 복잡도와 공간 복잡도

여기서 `n`은 `goal`의 길이다. 제한상 `n`은 최대 `cards1 길이 + cards2 길이`이고, 각 뭉치 길이가 최대 10이라 `n ≤ 20` 정도로 아주 작다.

| 풀이 | 시간 복잡도 | 공간 복잡도 | 메모 |
| --- | --- | --- | --- |
| 오답 (뒤에서부터) | `O(n)` | `O(1)` | 카운터 변수만 사용. 방향이 틀려 결과 자체가 오답 |
| 투 포인터 (정답) | `O(n)` | `O(1)` | 인덱스 두 개만 사용 |
| deque (정석) | `O(n)` | `O(n)` | 두 뭉치를 `deque`로 복사하는 만큼 추가 메모리 |

**시간**: 세 풀이 모두 `goal`을 딱 한 번 훑는다. 각 단계에서 하는 일은 길이 10 이하의 단어를 한두 번 비교하는 것뿐인데, 단어 길이가 상수(≤10)로 묶여 있어 비교 한 번을 상수 시간으로 본다. 그래서 전체는 `goal` 길이에 정비례하는 `O(n)`이다. 입력이 대략 두 배가 되면 비교 횟수도 대략 두 배가 되는 정도이고, 모든 카드 쌍을 맞대보는 중첩 반복(`O(n^2)`) 구조가 아니다. `deque.popleft()`는 큐의 왼쪽 끝 제거라 `O(1)`이므로(리스트의 `pop(0)`이 `O(n)`인 것과 다르다) deque 버전도 합쳐서 `O(n)`을 유지한다.

**제한과 연결**: 사실 이 문제는 `n ≤ 20`이라 `O(n^2)`, 심지어 `O(n^3)`으로 짜도 시간 초과는 나지 않는다. 다만 규칙(앞에서만 꺼내기)을 정확히 모델링하지 못하면 시간이 아니라 **정답이 틀린다**. 즉 이 문제의 난이도는 시간 복잡도가 아니라 "방향을 맞게 잡았는가"에 있다. (`n`이 `10^5`처럼 컸다면 `O(n^2)`는 `10^{10}`이 되어 시간 초과가 났겠지만, 여기선 그 지점이 아니다.)

**공간**: 오답·투 포인터는 변수 몇 개(카운터/인덱스)만 쓰므로 `O(1)`이다. deque 버전은 두 뭉치를 큐로 복사하므로 입력 크기에 비례하는 `O(n)` 추가 메모리를 쓴다. 입력이 작아 실제 체감 차이는 없지만, "추가 자료구조를 쓰면 그만큼 공간을 더 쓴다"는 점은 분류상 짚어둘 만하다.

## 이번 문제에서 배운 점

- 예제가 전부 통과해도 안심하면 안 된다. 특히 이 문제처럼 예제가 "카드를 전부 쓰는" 특수 케이스만 담고 있으면, 잘못된 방향의 풀이도 예제는 통과한다.
- 제한사항의 `2 ≤ goal 길이 ≤ 전체 길이`처럼 "안 써도 되는 경우"를 알려주는 한 줄을 반드시 반례로 떠올려 봐야 한다.
- 카드/스택처럼 "한쪽 끝에서만 꺼낼 수 있는" 문제는 **꺼내는 방향**이 곧 풀이의 정답/오답을 가른다. 투 포인터를 쓰느냐보다 어느 쪽 끝을 가리키느냐가 더 중요했다.
- 두 뭉치의 단어가 서로 겹치지 않는다는 제한 덕분에, "맞으면 바로 그 뭉치를 쓴다"는 단순 그리디가 애매함 없이 항상 옳다는 점도 같이 챙기면 좋다.
