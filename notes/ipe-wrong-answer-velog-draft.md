# 정보처리기사 필기 오답노트: 헷갈린 개념을 초보자 관점으로 다시 정리하기

> 방금 풀었던 정보처리기사 필기 기출 오답을 과목별로 다시 정리했다.  
> 목표는 "정답 번호를 외우기"가 아니라, 왜 그 보기가 틀렸는지 스스로 설명할 수 있게 만드는 것이다.

---

## 이번 오답에서 보인 패턴

이번 오답을 다시 보니 단순 암기보다 **용어의 경계**가 흔들린 문제가 많았다.

- 비슷한 말처럼 보이는 개념을 구분해야 하는 문제  
  예: 결합도/응집도, 테스트 드라이버/테스트 스텁, DAC/MAC/RBAC
- 범주를 외워야 하는 문제  
  예: GoF 패턴 분류, 라우팅 프로토콜 분류, xUnit 도구
- 정의의 한 단어가 바뀐 문제  
  예: 뷰는 물리 테이블이 아니라 가상 테이블, 릴레이션의 튜플은 순서가 없음
- 알고리즘의 실제 흐름을 손으로 따라가야 하는 문제  
  예: 이진 검색 비교 횟수, 버블 정렬 1회전, 트리 후위 순회

그래서 아래 정리는 문항을 그대로 베끼기보다, 내가 헷갈린 지점을 중심으로 풀어 썼다.

## 1과목 소프트웨어 설계

### 4번. 유스케이스 다이어그램 관계

**정답 포인트: 유스케이스 관계에 "구체화"는 포함되지 않는다.**

유스케이스 다이어그램에서 자주 나오는 관계는 다음 네 가지다.

| 관계 | 초보자식 이해 |
| --- | --- |
| 연관 | 액터가 유스케이스와 상호작용한다는 연결 |
| 포함 | 항상 같이 수행되는 공통 기능을 분리해서 재사용 |
| 확장 | 특정 조건에서만 추가로 수행되는 기능 |
| 일반화 | 더 일반적인 개념과 더 구체적인 개념의 상속 관계 |

여기서 헷갈리기 쉬운 말이 **구체화**다. 일반화의 반대 느낌이라 그럴듯해 보이지만, 유스케이스 다이어그램의 대표 관계 이름으로는 보통 **일반화**를 기억해야 한다.

### 9번. 다형성과 오버로딩/오버라이딩

**정답 포인트: 오버로딩은 메소드 이름이 같고, 매개변수의 개수나 타입이 다르다.**

다형성은 같은 메시지를 보내도 객체의 실제 타입에 따라 다르게 동작할 수 있는 성질이다. 초보자 입장에서는 이렇게 생각하면 편하다.

- `draw()`라는 같은 요청을 보낸다.
- 원 객체는 원을 그리고, 사각형 객체는 사각형을 그린다.
- 호출하는 쪽은 `draw()`만 알면 되고, 실제 동작은 객체가 알아서 한다.

여기서 두 용어를 꼭 구분해야 한다.

| 개념 | 핵심 |
| --- | --- |
| 오버라이딩 | 부모 클래스의 메소드를 자식 클래스가 다시 정의 |
| 오버로딩 | 같은 이름의 메소드를 매개변수 차이로 여러 개 정의 |

오버로딩은 **메소드명이 다르다**가 아니라 **메소드명은 같다**가 핵심이다.

### 15번. GoF 디자인 패턴 분류

**정답 포인트: Builder는 구조 패턴이 아니라 생성 패턴이다.**

GoF 패턴은 크게 생성, 구조, 행위 패턴으로 나뉜다.

| 분류 | 관심사 | 예시 |
| --- | --- | --- |
| 생성 패턴 | 객체를 어떻게 만들 것인가 | Builder, Factory Method, Singleton |
| 구조 패턴 | 객체나 클래스를 어떻게 조립할 것인가 | Adapter, Bridge, Proxy, Decorator |
| 행위 패턴 | 객체들이 어떻게 책임을 나누고 소통할 것인가 | Observer, Strategy, Command |

`Builder`는 복잡한 객체를 단계적으로 만들 때 쓰는 패턴이다. 그래서 "구조를 조립한다" 느낌에 끌리면 틀리기 쉽지만, 분류상으로는 **객체 생성 방식**을 다루므로 생성 패턴이다.

## 2과목 소프트웨어 개발

### 22번. 이진 검색 비교 횟수

**정답 포인트: 14를 찾을 때 비교 횟수는 3회다.**

이진 검색은 정렬된 데이터에서 가운데 값을 확인하고, 찾는 값이 더 크면 오른쪽 절반만, 더 작으면 왼쪽 절반만 다시 본다.

예를 들어 `1`부터 `15`까지 정렬된 값에서 `14`를 찾으면:

1. 가운데 `8`과 비교한다. `14`는 더 크므로 오른쪽을 본다.
2. 남은 범위 `9~15`의 가운데 `12`와 비교한다. `14`는 더 크다.
3. 남은 범위 `13~15`의 가운데 `14`와 비교한다. 찾았다.

그래서 비교는 총 3번이다. 이진 검색의 핵심은 **한 번 비교할 때마다 후보 범위가 거의 절반으로 줄어든다**는 점이다.

### 25번. 테스트 케이스 작성 순서

**정답 포인트: 테스트 케이스는 테스트 목표와 방법을 정한 뒤 작성한다.**

테스트 케이스는 아무 입력값이나 적어보는 문서가 아니다. 먼저 "무엇을 확인할지"와 "어떤 방식으로 확인할지"가 정해져야 한다.

흐름은 이렇게 보는 게 자연스럽다.

1. 테스트 목표를 정한다.
2. 테스트 방법과 범위를 정한다.
3. 입력값, 실행 조건, 예상 결과를 가진 테스트 케이스를 작성한다.
4. 실제 결과와 예상 결과를 비교한다.

그리고 이때 통과/실패를 판단하는 기준을 **테스트 오라클**이라고 한다.

### 27번. DRM

**정답 포인트: DRM은 불법 유통과 복제를 막기 위한 보안 장치를 포함한다.**

DRM은 디지털 콘텐츠의 사용 권한을 관리하는 기술이다. 단순히 "누가 샀는지 기록"하는 수준이 아니라, 콘텐츠가 유통되는 과정에서 권한 확인, 라이선스 발급, 복제 방지 같은 기능까지 다룬다.

초보자식으로 보면:

- 콘텐츠: 영화, 음악, 전자책 같은 디지털 자료
- 라이선스: 이 사용자가 어디까지 이용할 수 있는지 알려주는 권한표
- 클리어링 하우스: 라이선스를 발급하고 권한을 관리하는 역할
- 보안 컨테이너: 콘텐츠를 안전하게 감싸 불법 복제를 어렵게 하는 장치

따라서 DRM이 보안을 고려하지 않는다는 설명은 틀리다.

### 31번. 선형 검색과 정렬 여부

**정답 포인트: 선형 검색은 데이터가 정렬되어 있지 않아도 사용할 수 있다.**

선형 검색은 앞에서부터 하나씩 비교하는 가장 단순한 검색 방식이다.

```text
찾는 값: 7
데이터: 3, 10, 2, 7, 5

3인가? 아니오
10인가? 아니오
2인가? 아니오
7인가? 예
```

정렬이 필요하지 않은 대신, 운이 나쁘면 끝까지 다 확인해야 한다. 반대로 이진 검색은 가운데를 기준으로 반씩 줄여가야 하므로 **정렬된 데이터**가 필요하다.

### 32번. 버블 정렬 PASS 1

**정답 포인트: `9, 6, 7, 3, 5`를 오름차순 버블 정렬하면 PASS 1 결과는 `6, 7, 3, 5, 9`다.**

버블 정렬은 옆에 붙어 있는 두 값을 비교해서 큰 값을 오른쪽으로 보낸다. 오름차순 정렬에서는 한 번의 PASS가 끝나면 가장 큰 값이 맨 뒤로 이동한다.

초기 상태:

```text
9, 6, 7, 3, 5
```

PASS 1:

```text
9와 6 비교 -> 9가 크므로 교환: 6, 9, 7, 3, 5
9와 7 비교 -> 교환: 6, 7, 9, 3, 5
9와 3 비교 -> 교환: 6, 7, 3, 9, 5
9와 5 비교 -> 교환: 6, 7, 3, 5, 9
```

그래서 1회전 결과는 `6, 7, 3, 5, 9`다.

### 35번. 테스트 드라이버와 테스트 스텁

**정답 포인트: 필요한 데이터를 넘겨주고 결과를 받는 가상 모듈은 테스트 드라이버다.**

단위 테스트에서는 아직 완성되지 않은 주변 모듈을 임시 모듈로 대신할 수 있다. 이때 두 이름이 자주 헷갈린다.

| 구분 | 역할 |
| --- | --- |
| 테스트 드라이버 | 테스트 대상 모듈을 호출하는 임시 상위 모듈 |
| 테스트 스텁 | 테스트 대상 모듈이 호출하는 임시 하위 모듈 |

쉽게 말하면 드라이버는 "테스트 대상을 실행시켜 주는 쪽"이고, 스텁은 "테스트 대상이 호출했을 때 대신 응답해 주는 쪽"이다.

### 37번. 후위 순회

**정답 포인트: 후위 순회는 `Left -> Right -> Root` 순서다.**

트리 순회는 루트를 언제 방문하느냐로 이름이 갈린다.

| 순회 | 순서 | 루트 위치 |
| --- | --- | --- |
| 전위 순회 | Root -> Left -> Right | 앞 |
| 중위 순회 | Left -> Root -> Right | 가운데 |
| 후위 순회 | Left -> Right -> Root | 뒤 |

이 문항의 트리에서는 후위 순회 결과가 `D -> B -> G -> H -> E -> F -> C -> A`였다. 그림 문제가 나오면 먼저 작은 서브트리부터 묶고, 각 묶음마다 **왼쪽, 오른쪽, 루트** 순서로 읽으면 실수를 줄일 수 있다.

### 40번. 단위 테스트 도구

**정답 포인트: IgpUnit은 대표적인 xUnit 계열 단위 테스트 도구가 아니다.**

단위 테스트 프레임워크는 언어별로 이름이 조금씩 다르다.

- Java: JUnit
- C++: CppUnit
- .NET: NUnit
- 웹 테스트 쪽: HttpUnit

시험에서는 낯선 이름을 섞어 놓고 고르게 하는 경우가 많다. `xUnit` 계열 이름을 묶어서 기억해 두면 좋다.

## 3과목 데이터베이스 구축

### 41번. BCNF

**정답 포인트: 모든 결정자가 후보키이면 BCNF다.**

정규형 문제에서는 "결정자"와 "후보키"를 구분해야 한다.

- 결정자: 어떤 속성의 값을 결정하는 속성
- 후보키: 튜플을 유일하게 식별할 수 있고, 더 줄일 수 없는 최소 속성 집합

BCNF는 제3정규형보다 더 강한 조건으로, 모든 함수적 종속에서 **결정자가 후보키**여야 한다.

### 42번. 트랜잭션 원자성

**정답 포인트: 모두 반영되거나 전혀 반영되지 않는 성질은 Atomicity다.**

트랜잭션의 ACID는 다음처럼 기억하면 좋다.

| 성질 | 의미 |
| --- | --- |
| Atomicity | 모두 성공하거나 모두 취소 |
| Consistency | 실행 전후 데이터베이스 규칙이 유지됨 |
| Isolation | 동시에 실행되어도 서로 간섭하지 않는 것처럼 보임 |
| Durability | 커밋된 결과는 장애가 나도 보존 |

은행 이체를 예로 들면, 내 계좌에서 돈이 빠졌는데 상대 계좌에 입금되지 않으면 안 된다. 출금과 입금은 함께 성공하거나 함께 취소되어야 한다. 이것이 원자성이다.

### 46번. 저장 레코드 설계와 트랜잭션 모델링

**정답 포인트: 트랜잭션 모델링은 물리적 저장 레코드 양식 설계의 고려사항이 아니다.**

물리적 데이터베이스 설계에서는 실제 저장 방식에 가까운 요소를 고려한다.

- 데이터 타입
- 데이터 값의 분포
- 접근 빈도
- 저장 구조

반면 트랜잭션 모델링은 업무가 어떤 데이터 흐름을 가지는지 파악하는 쪽에 가깝다. 그래서 물리적 저장 레코드 양식 자체의 고려사항으로 보기 어렵다.

### 49번. 릴레이션의 특징

**정답 포인트: 릴레이션에서 튜플은 특정 순서를 가지지 않는다.**

데이터베이스의 릴레이션은 표처럼 보이지만, 엑셀처럼 "몇 번째 줄" 자체가 의미를 갖는다고 보면 안 된다.

릴레이션의 대표 특징:

- 튜플은 서로 구별된다.
- 튜플 사이에는 순서가 없다.
- 속성 이름은 릴레이션 안에서 유일하다.
- 속성 값은 더 쪼개지지 않는 원자값이어야 한다.

조회 결과가 어떤 순서로 보이길 원한다면 SQL에서 `ORDER BY`를 써야 한다.

### 50번. 뷰

**정답 포인트: 뷰는 물리적으로 저장된 기본 테이블이 아니라 가상 테이블이다.**

뷰는 하나 이상의 기본 테이블에서 필요한 부분을 보여주는 가상 테이블이다.

```sql
CREATE VIEW active_users AS
SELECT id, name
FROM users
WHERE status = 'ACTIVE';
```

위 예시에서 `active_users`는 실제 데이터를 새로 전부 저장하는 테이블이라기보다, `users` 테이블을 특정 조건으로 바라보는 창에 가깝다. 그래서 뷰는 조회에는 편리하지만, 갱신에는 제약이 생길 수 있다.

### 51번. Partially Committed

**정답 포인트: 마지막 연산은 끝났지만 아직 최종 반영 전인 상태는 Partially Committed다.**

트랜잭션 상태를 흐름으로 보면 이해가 쉽다.

```text
Active -> Partially Committed -> Committed
       -> Failed -> Aborted
```

`Partially Committed`는 모든 연산이 끝났지만, 아직 데이터베이스에 최종 확정된 것은 아닌 중간 상태다. 커밋까지 완료되어야 `Committed`라고 부른다.

### 53번. 후보키

**정답 포인트: 유일성과 최소성을 모두 만족하는 키는 후보키다.**

키 문제는 두 단어로 정리할 수 있다.

- 유일성: 튜플을 서로 구별할 수 있어야 한다.
- 최소성: 식별에 꼭 필요한 속성만 남아 있어야 한다.

후보키는 이 두 조건을 모두 만족한다. 슈퍼키는 유일성은 만족하지만 최소성은 만족하지 않을 수 있다. 그래서 후보키는 슈퍼키 중에서도 군더더기가 제거된 키라고 볼 수 있다.

### 54번. 개념적 설계 단계

**정답 포인트: 트랜잭션 인터페이스 설계는 개념적 설계가 아니라 논리적 설계 쪽에 가깝다.**

데이터베이스 설계 단계는 대략 이렇게 흐른다.

| 단계 | 초점 |
| --- | --- |
| 개념적 설계 | 현실 세계를 개념적으로 모델링, E-R 다이어그램 작성 |
| 논리적 설계 | DBMS가 이해할 수 있는 논리 스키마로 변환 |
| 물리적 설계 | 실제 저장 구조, 인덱스, 접근 경로 등을 설계 |

개념적 설계는 특정 DBMS에 묶이지 않는 큰 그림을 그리는 단계다.

### 55번. 기본키

**정답 포인트: 검색할 때 기본키가 반드시 필요한 것은 아니다.**

기본키는 튜플을 유일하게 구별하기 위한 핵심 속성이다. 기본키로 지정되면 보통 `NOT NULL`이고, 다른 테이블의 외래키가 참조할 수도 있다.

하지만 검색은 기본키가 없어도 가능하다.

```sql
SELECT *
FROM students
WHERE name = '민수';
```

물론 기본키나 인덱스를 이용하면 검색이 더 빠를 수는 있다. 하지만 "검색하려면 반드시 기본키가 있어야 한다"는 말은 틀리다.

## 4과목 프로그래밍 언어 활용

### 64번. IP 프로토콜 필드

**정답 포인트: Packet Length는 IP 헤더를 포함한 전체 패킷 길이를 나타낸다.**

IP 헤더에는 버전, 헤더 길이, 전체 길이, TTL 같은 필드가 들어간다.

| 필드 | 의미 |
| --- | --- |
| Version | IP 버전 |
| Header Length | 헤더 길이 |
| Packet Length | 헤더를 포함한 전체 패킷 길이 |
| TTL | 패킷이 네트워크에서 살아남을 수 있는 시간/홉 제한 |

여기서 Packet Length를 "헤더 제외"라고 하면 틀린 설명이다. 또한 IPv4의 전체 길이 필드는 16비트라 최대 크기도 `2^16 - 1` 바이트 기준으로 기억해야 한다.

### 66번. RIP 라우팅 프로토콜

**정답 포인트: RIP는 EGP가 아니라 IGP다.**

RIP는 내부 네트워크 안에서 라우팅 정보를 교환하는 프로토콜이다.

- 분류: IGP
- 메트릭: 홉 카운트
- 알고리즘: Bellman-Ford
- 방식: 이웃 라우터에게 받은 정보로 라우팅 테이블 갱신

`IGP`는 조직 내부의 라우팅, `EGP`는 서로 다른 자율 시스템 사이의 라우팅으로 구분하면 된다.

### 67번. HRN 스케줄링

**정답 포인트: 대기 시간과 서비스 시간을 함께 고려하는 방식은 HRN이다.**

HRN은 Highest Response-ratio Next의 약자다. 응답률이 가장 높은 프로세스를 먼저 실행한다.

```text
응답률 = (대기 시간 + 서비스 시간) / 서비스 시간
```

서비스 시간이 짧은 작업만 계속 먼저 처리하면 긴 작업이 오래 기다릴 수 있다. HRN은 대기 시간이 길어질수록 응답률도 올라가게 해서, 오래 기다린 작업도 선택될 가능성을 높인다.

### 77번. 사용자 수준 스레드의 장점

**정답 포인트: 사용자 수준 스레드는 커널 모드 전환 없이 스레드 교환이 가능해 오버헤드가 작다.**

스레드는 사용자 수준 스레드와 커널 수준 스레드로 나눌 수 있다.

| 구분 | 특징 |
| --- | --- |
| 사용자 수준 스레드 | 커널 개입이 적어 전환이 빠름 |
| 커널 수준 스레드 | 커널이 각 스레드를 인식하고 스케줄링 가능 |

사용자 수준 스레드는 빠른 전환이 장점이다. 반면 한 스레드가 시스템 호출로 막히면 전체 프로세스가 영향을 받을 수 있다는 단점도 있다.

### 78번. 내용 결합도

**정답 포인트: 다른 모듈의 내부 기능이나 내부 자료를 직접 참조하면 내용 결합도다.**

결합도는 모듈끼리 얼마나 강하게 얽혀 있는지를 뜻한다. 결합도는 낮을수록 좋다.

내용 결합도는 가장 좋지 않은 결합도에 가깝다. 한 모듈이 다른 모듈의 내부 구현을 직접 건드리면, 상대 모듈이 조금만 바뀌어도 함께 깨질 수 있기 때문이다.

초보자식으로 말하면, 남의 방에 허락 없이 들어가 서랍을 직접 뒤지는 구조다. 좋은 설계는 필요한 요청만 정해진 문으로 전달하는 구조다.

### 80번. 모듈화와 응집도/결합도

**정답 포인트: 모듈 사이의 상호 의존 정도는 응집도가 아니라 결합도다.**

두 단어는 방향이 다르다.

| 개념 | 보는 위치 | 좋은 상태 |
| --- | --- | --- |
| 응집도 | 모듈 내부 요소들이 얼마나 관련 있는가 | 높을수록 좋음 |
| 결합도 | 모듈과 모듈 사이가 얼마나 의존하는가 | 낮을수록 좋음 |

좋은 모듈은 자기 안에서는 관련 있는 일끼리 잘 뭉쳐 있고, 바깥 모듈과는 덜 얽혀 있다. 즉 **높은 응집도, 낮은 결합도**가 목표다.

## 5과목 정보시스템 구축 관리

### 82번. TCP Wrapper

**정답 포인트: 외부 접속을 허용하거나 거부하는 접근 제어 유틸리티는 TCP Wrapper다.**

TCP Wrapper는 외부 컴퓨터가 서버에 접속하려 할 때, 허용된 대상인지 확인해서 접근을 통제하는 도구로 이해하면 된다.

핵심은 "접속 요청이 들어왔을 때 허용 목록/차단 목록을 보고 판단한다"는 점이다.

### 83번. Zing

**정답 포인트: 10cm 이내의 매우 가까운 거리에서 고속 데이터를 전송하는 초고속 근접무선통신 기술은 Zing이다.**

NFC라는 말에 익숙해서 모든 근접 통신을 NFC로만 생각하면 틀리기 쉽다. 이 문항에서는 초고속 근접무선통신 기술 이름으로 **Zing**을 묻고 있다.

키워드는 이렇게 묶어 외우면 좋다.

```text
초근접 + 고속 전송 + 키오스크 접촉 = Zing
```

### 87번. Mesh Network

**정답 포인트: 여러 노드가 그물처럼 연결되어 통신하는 구조는 Mesh Network다.**

Mesh Network는 하나의 중앙 장비에만 의존하지 않고, 여러 장비가 서로 연결되어 데이터를 전달할 수 있는 네트워크 구조다.

장점은 일부 경로가 끊겨도 다른 경로를 통해 통신할 수 있다는 점이다. 그래서 "그물망", "다중 경로", "노드들이 서로 연결" 같은 표현이 나오면 Mesh Network를 떠올리면 된다.

### 95번. RBAC

**정답 포인트: 직무나 역할에 따라 권한을 부여하는 방식은 RBAC다.**

접근 통제는 기준에 따라 이름이 달라진다.

| 방식 | 기준 |
| --- | --- |
| DAC | 소유자가 접근 권한을 결정 |
| MAC | 보안 등급과 정책에 따라 강제 통제 |
| RBAC | 사용자의 역할에 따라 권한 부여 |

회사 시스템을 예로 들면, "인사팀 직원은 인사 정보를 볼 수 있다", "회계 담당자는 결제 자료를 볼 수 있다"처럼 역할에 따라 권한을 묶는 방식이 RBAC다.

### 99번. SDN

**정답 포인트: 네트워크 제어 기능을 소프트웨어로 분리해 중앙에서 관리하는 기술은 SDN이다.**

SDN은 Software Defined Networking의 약자다. 기존 네트워크 장비에서는 데이터 전달 기능과 제어 기능이 장비 안에 함께 들어 있는 경우가 많았다. SDN은 제어 영역을 소프트웨어적으로 분리해서 더 유연하게 관리하려는 접근이다.

초보자식으로 보면:

- 기존 방식: 각 네트워크 장비가 자기 판단을 많이 한다.
- SDN 방식: 중앙 컨트롤러가 전체 흐름을 보고 정책을 내려준다.

그래서 네트워크 구성을 더 빠르게 바꾸고, 정책을 중앙에서 관리하기 좋다.

## 한 번 더 묶어서 외울 것들

### 1. "좋은 설계" 문제의 기본 방향

- 응집도는 높게
- 결합도는 낮게
- 내부 구현을 직접 건드리지 않게
- 공통 기능은 재사용 가능하게

### 2. 테스트 용어

- 테스트 케이스: 입력값, 실행 조건, 예상 결과의 묶음
- 테스트 오라클: 성공/실패를 판단하는 기준
- 테스트 드라이버: 테스트 대상을 호출하는 임시 상위 모듈
- 테스트 스텁: 테스트 대상이 호출하는 임시 하위 모듈

### 3. 데이터베이스에서 자주 나오는 반대말

- 기본 테이블 vs 뷰: 뷰는 가상 테이블
- 슈퍼키 vs 후보키: 후보키는 유일성 + 최소성
- 튜플 순서 있음 vs 없음: 릴레이션의 튜플에는 순서가 없음
- Partially Committed vs Committed: 마지막 연산 완료와 최종 확정은 다름

### 4. 알고리즘 문제는 손으로 한 번 따라가기

이진 검색, 버블 정렬, 트리 순회 문제는 설명을 외우는 것보다 손으로 직접 한 단계씩 적는 편이 더 정확했다.

- 이진 검색: 한 번 비교할 때마다 범위가 절반으로 줄어든다.
- 버블 정렬: 한 PASS가 끝나면 가장 큰 값이 오른쪽 끝으로 간다.
- 후위 순회: 왼쪽, 오른쪽, 루트 순서로 읽는다.
